# F0001 设计：规格、控制状态和实现版本

## 组成

架构师技能提供决策流程，根 `AGENTS.md` 为所有模型提供入口。厂商无关的编码说明链接到同一份协作协议，避免两套角色规则出现状态定义冲突。模板随技能分发；具体功能、任务和证据放在项目 `docs/`。

`workflow.py` 提供结构校验和下一动作建议，不代替审查，也不修改 Git。只依赖 Python 标准库和 Git CLI。协议是行为规则，脚本仅落实其中可确定检查的部分。

## Git 数据模型

| 数据 | 存储位置 | 版本关联 |
| --- | --- | --- |
| 需求/设计/任务契约 | 控制分支 docs | 任务绑定 spec_commit |
| 当前任务状态 | 控制分支 task.json | 每次转换另起提交 |
| 实现和实施报告 | task/Txxxx-* 分支 | submission_head |
| 审查结果 | 控制分支 reviews/round-N.json | reviewed_base、reviewed_head |
| 合入与集成验证 | 控制分支及状态 | integrated_commit、integration_evidence |

精确状态机与字段约束见 [协作协议](../../../.agents/skills/architect-orchestrator/references/workflow.md)。字段样例见技能的 task/review JSON 模板；保留 null 表示尚未发生，不能填写虚构 SHA。

## 一次成功交接

1. 架构师提交需求、设计、任务说明，得到 S；随后提交 READY 状态，绑定 S。
2. 编码者读取同步后的主分支 B，将领取状态提交为 C 并 push；成功后从 C 创建任务分支。
3. 编码者提交代码和实施报告 H 并 push；主分支另起状态提交记录 IN_REVIEW 和 H。
4. 架构师审查 B..H，对照 S 的契约，提交审查记录和 ACCEPTED。
5. 架构师确认远程任务 HEAD 仍为 H，创建合并提交 M，运行集成检查。
6. 架构师另起状态提交记录 DONE、M 及集成证据并 push。下一次读取队列才可领取下项。

S、H、M 均在后续提交中被引用，避免提交自引用。任务分支自 C 后不修改控制文件，所以主分支状态可正常保留而不会随代码合入倒退。

## 校验与边界

校验覆盖 JSON 字段、任务唯一性、依赖与循环、活动任务数量、规格文件存在、Git 提交可达关系、实施报告、审查维度与验收覆盖、审查版本、完成合入和集成证据。结构正确不意味着行为正确；审查者仍需阅读代码并运行相关验证。

`next` 在有效快照上给出唯一下一动作。领取仍需通过主分支 fast-forward push 竞争；工具不宣称预留成功。无业务任务时返回 IDLE。读取队列前需要 fetch，因为本地引用无法代表尚未获取的远程更新。

## 验证方案

行为测试使用临时 Git 仓库，验证正常领取和依赖、活动任务阻止领取、审查漂移、无证据完成、基线/合入关系与异常输入。交付前运行测试、模板和链接检查、技能校验以及 Git diff 检查。

模型执行器、自动唤醒、通知和平台身份权限保持在外部。未来若增加这些组件，应先以新需求描述运行方式、恢复条件和权限，再设计实现。
