# 多项目管理规则

依据用户在 2026-10-24 的决定：独立项目各用独立 Git 仓库，由架构师在立项时准备仓库，再向编码 Agent 发布任务。

## 仓库职责与事实来源

| 位置 | 负责内容 |
| --- | --- |
| 管理仓库 `cason37c/agent_work` | 公共协作规则、模板、工具、个人入口源码与项目索引；协作框架自身的维护 |
| 各项目仓库 | 本项目的需求、设计、任务状态、代码、实施报告、审查和验收记录 |

管理仓库中的 `docs/projects.json` 是项目定位索引。项目任务状态以所属仓库控制分支的 `docs/tasks/T*/task.json` 为准。总览从各仓库读取状态，并注明读取的分支、提交及未同步情况；索引不复制当前任务、完成百分比或审查结论。

## 启动与选择项目

1. 用户明确提供仓库时使用该仓库；提供项目名称或 ID 时查询管理仓库索引，匹配 `id`、`name` 或 `aliases`。已知目标的新功能继续在原项目仓库实现。
2. 用户未指定项目但本会话已确认目标时继续该项目；新会话的当前目录仅在其远程与索引中的唯一项目匹配时用作目标。目录名、最近更新时间和唯一索引条目本身不构成项目选择。
3. 只要求启动模式、尚未确定项目时，加载管理规则与项目索引，简要报告可选项目或空索引，邀请用户描述需求。多个匹配或“继续”没有可确认目标时，集中询问项目选择，继续不依赖选择的整理工作。
4. 新需求属于独立产品时进入立项；属于已有产品时使用原仓库。归属会改变产品边界且无法从上下文确定时，先澄清再创建仓库。
5. 选定后核对本地仓库的远程地址。优先复用匹配的现有克隆；不存在时在允许的工作目录独立克隆，保留其他目录内容。读取目标仓库的 `AGENTS.md`、项目配置、架构师技能及其协作协议，并同步 Git 后恢复任务。

本地路径是定位提示，仓库身份以托管主机、所有者与仓库名为准；HTTPS 与 SSH 地址可对应同一仓库。网络或认证失败时报告实际状态，继续本地整理，但任务领取和远程交接仍需成功写入目标远程。

## 独立项目立项

架构师在首个编码任务发布前完成以下准备：

1. 从需求确定项目名称、仓库归属和已有仓库是否可复用。新远程仓库的所有者、名称与可见性依据用户已给出的信息或已确认默认值；关键缺失信息集中询问。本规则不授予额外外部操作权限。
2. 创建或接入独立仓库并核对远程。远程创建暂不可用时，可在允许目录初始化本地仓库并准备草稿，明确标注尚未远程交接；业务规格和代码仍保存在该项目目录。
3. 在项目仓库落地协作文件：合并 `AGENTS.md` 入口；引入 `.agents/skills/architect-orchestrator/`、`docs/agents/implementer.md`、`docs/project/working-agreement.md`、本文件、`docs/project/config.json` 和 `scripts/workflow.py`。需要保留工作流回归检查时引入 `tests/test_workflow.py`。现有文件逐项合并，保留项目原有约束。
4. 将配置中的远程、控制分支和 `project_checks` 调整为该项目的实际环境；同步协议中的示例命令。按实际需要建立 `docs/features/` 与 `docs/tasks/`，不复制管理仓库的历史需求、任务或项目索引。规则来源记录在项目的 `docs/project/workflow-source.json`，包含管理仓库地址和引入规则的完整提交 SHA。
5. 在项目仓库编写需求、设计、任务及验收规则，按本地配置运行校验和适当检查。仓库和初始协作文件可被远程读取后，在管理索引登记项目；只完成本地准备时暂不登记正式条目。
6. 按项目内协议先提交规格，再绑定规格 SHA 发布 `READY` 并推送。交接提供项目名称、仓库地址、控制分支、任务 ID、规格提交和下一动作。远程可读取才算交接完成。

用户明确要求沿用一个已有多产品仓库时，尊重其仓库边界，先在该仓库明确模块范围和共享验证方式；不擅自拆分历史代码。`agent_work` 中现存的协作框架文档和工具属于管理仓库自身。

## 项目索引

索引 JSON 的 `schema_version` 为 `1`，`projects` 是项目记录数组；空数组表示尚无登记业务项目。每个记录具有以下字段：

| 字段 | 约定 |
| --- | --- |
| `id` | 稳定且唯一的小写字母、数字与连字符标识；改名保留 ID |
| `name` | 用户使用的项目名称 |
| `aliases` | 名称别名数组；允许空数组，匹配多个条目时澄清 |
| `summary` | 一句话说明产品用途 |
| `repository_url` | 已存在且确认的远程地址；一个远程登记一次 |
| `control_branch` | 项目控制分支，须与该仓库配置一致 |
| `lifecycle` | `active` 或 `archived`，表示项目生命周期，不表示任务进度 |
| `preferred_local_path` | 可选本地定位提示；其他机器可以查找同一远程或重新克隆 |

架构师维护索引，修改前同步管理仓库，提交后普通 fast-forward 推送。项目仓库和管理索引是两次独立 Git 写入：先确保项目仓库已存在并可读取，再登记索引；索引写入失败时保留项目成果，报告“项目已准备，索引尚未更新”，恢复后补登记。

## 项目内执行与跨项目恢复

每个项目独立编号功能与任务，任务 ID 的完整身份是“仓库地址 + 任务 ID”。工作流脚本只检查当前仓库，每个项目内部仍一次一个活动任务。跨项目是否同时推进由用户或宿主执行器安排；切换项目不自动取消或接管另一个项目的活动任务。

`requires` 只引用同仓库任务。跨项目依赖在需求或设计中登记目标仓库、依赖版本与可观察验收条件，架构师确认满足后再发布任务。规则和索引不提供后台调度、自动唤醒或模型启动。

重新进入项目时读取目标远程控制分支、固定规格、提交和审查记录来恢复。归档时先处理活动任务，再把索引中的 `lifecycle` 改为 `archived`；保留仓库和全部历史。恢复归档项目时明确恢复为 `active`，再检查项目内任务状态。

## 公共规则升级

项目使用自己仓库中已提交的规则；管理仓库的新规则通过各项目自己的 Git 变更引入，记录来源提交并运行该项目检查，保持活动任务的规格绑定。通用规则变更在管理仓库维护，项目专有约束写入该项目。

个人入口的受版本控制源码位于管理仓库 `skills/architect/`，安装目录为个人 `skills/architect/`。更新入口时同步源码与已安装副本，验证二者一致；本地仓库路径在入口的 `references/project.json` 中配置。项目索引和路由的行为由本文件约定，现有 `workflow.py validate/next` 只验证项目内任务，不验证项目路由或索引。
