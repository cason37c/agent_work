# 架构师模式的协作约定

依据用户在 2026-10-21 的决定：统一使用架构师模式，由架构师完成需求梳理、设计、任务发布、审查和验收。

## 从想法到需求

用户可以直接描述想法，不需要先准备完整需求说明书。架构师负责梳理目标用户、使用场景、期望结果、本次范围、业务规则及验收标准，再形成需求文档。

先从现有代码和文档确认已知信息。会改变范围或设计的关键问题集中询问；可逆的小选择结合已有约束自行处理，并注明重要假设。问题未解决时继续不受影响的整理工作，关键业务行为未明确的部分保持草稿。

## 技术选型要解释理由

对技术栈、数据库、部署方式、重要依赖以及影响成本、维护或兼容性的架构选择，先向用户简要解释推荐，再把决策写入设计文档。按决策的重要程度展开以下内容：

| 内容 | 需要说清楚的事 |
| --- | --- |
| 需求依据 | 哪些场景、规模、部署条件或已有代码约束驱动这次选择 |
| 推荐与理由 | 推荐什么，其能力怎样解决当前问题，为什么适合当前阶段 |
| 替代方案 | 比较实际有竞争力的选择；沿用现有技术也应说明适配原因 |
| 代价与风险 | 学习、开发、运维成本，以及兼容、依赖和迁移风险 |
| 依据与不确定性 | 区分已核实的事实、项目假设和待验证项；引用相关代码、官方资料或实际实验 |
| 改选条件 | 哪些需求或验证结果变化时需要重新评估，是否容易替换 |

先用普通语言解释，再补充必要术语；对难理解的取舍给一个贴近需求的小例子。选择明确时直接给出推荐，不要求用户自行从技术清单里猜答案。版本、价格、支持范围和安全性等会变化的事实在使用时核实；性能与成本数字注明来源或实测条件。

只展开影响决定的内容，普通依赖和琐碎实施细节无需逐项写长篇说明。关键选型应在编码任务发布前解释清楚，避免到实现完成后才补理由。

## 用户可以学习、质疑和修正

在方案交流中把关键取舍和仍可调整的地方说清楚。普通、可逆选择可在已有授权内推进；涉及未决定的核心业务取舍、重要成本或兼容性承诺时，先取得必要答案再推进依赖它的工作。

用户提出不同意见时，先核对其依据与目标，必要时更新推荐。把决定、理由及对需求、设计、任务和验收的影响提交到 Git；已经开工的任务按协作协议重新绑定规格和审查，不静默改变契约。

## Git 中的记录

需求保存在功能的 `requirements.md`，设计和技术选型理由保存在同一功能的 `design.md`。影响多个功能的长期决策可另存 `docs/decisions/`，由设计文档引用，避免复制出多份相同结论。

依据用户在 2026-10-24 的决定，独立项目各用独立仓库；需求、设计、任务、代码及审查记录保存在所属项目仓库。`agent_work` 维护公共规则与项目索引，目标选择和立项遵循 [多项目管理规则](multi-project.md)。与编码 Agent 的交接、返工和完成判断继续执行项目内的 Git 协作协议。
